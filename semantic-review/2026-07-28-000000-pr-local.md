# Multi-device catalog pull and reconciliation

The change introduces an authenticated, cursor-based catalog pull and applies category/item events into each device’s SQLite inventory after the outbox push succeeds. However, category edits, reordering, and deletes never enter the outbox; those changes cannot reach another device. The app also hard-gates synchronization to owner memberships even though the pull RPC is authorized for every active shop member, leaving staff phones unable to pull catalog updates. Watch for: **confirmed** catalog category state silently diverges across devices, and **confirmed** non-owner devices cannot receive catalog changes through the app.

**Verdict**: NEEDS_CHANGES

## High-level view

Catalog propagation is push-then-pull. The cursor advances only in the SQLite transaction that applies a received page, so interrupted reconciliation retries rather than skips that page.

Mapped remote deletes reconcile safely with the local category-to-item foreign key, but that path only processes server events. Local category mutations never create those events, so category state diverges even while item synchronization succeeds.

The database authorization permits active owner, admin, and staff memberships to call `pull_catalog_changes`, but the app returns before `runSync` unless the membership is an owner. A staff account on a second phone therefore has no application path to consume the remote catalog.

<details>
<summary>Details</summary>

## Category changes have no route into the remote event stream

`App.tsx` queues only `queueItemUpsert` after an item save and `queueItemDelete` during item deletion. `saveCategoryHandler`, `deleteCategoryHandler`, and `moveCategory` write directly to SQLite and refresh UI state without creating `category_upsert` or `category_delete` outbox entries. The only time a category is incidentally queued is when an item referencing it is subsequently saved.

That produces durable divergence: rename, recolor, reorder, delete, and newly created-but-unused categories on phone A create no `apply_catalog_sync_operation` call, no PostgreSQL trigger event, and nothing for `pull_catalog_changes` to return to phone B. A later item edit can eventually publish a category snapshot, but a category deletion cannot be recovered that way because no item references the deleted category. Queue the category operation atomically with each successful local category mutation; for reordering, queue snapshots for every category whose position changes.

## The app denies receiving updates to non-owner phones

`pull_catalog_changes` uses `public.has_shop_role(p_shop_id)`, allowing any active owner, admin, or staff member to read only its shop’s cursor stream. But `syncNow` in `App.tsx` returns when `membership?.role !== 'owner'`, before it calls `runSync`; the visible Sync screen uses that same callback.

As a result, a staff user on a second phone cannot advance its local cursor or reconcile the item/category records uploaded by the owner. This is **confirmed** behavior because the client-side guard prevents the network call. If staff devices are expected to receive the shared catalog, separate pull authorization from owner-only migration controls and allow active members to pull. If synchronization must be owner-only, the server RPC should enforce the same policy and the product requirement must exclude staff-operated phones.

</details>
