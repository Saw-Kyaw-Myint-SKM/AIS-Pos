# First-owner serialization and cloud-session teardown

The first-owner bootstrap now takes an exclusive, persistent database claim before it checks for or creates a shop. That closes the concurrent-bootstrap path: only one invocation can retain `owner_bootstrap_guard.id = true`, and a successful owner leaves the claim in place. Local logout and Supabase disconnect, however, both suppress a failed cloud sign-out and then continue to remove the local session or configuration. **Watch for:** **confirmed** a failed Supabase sign-out can leave its persisted session usable on the device after the app presents a logged-out or disconnected state.

**Verdict**: NEEDS_CHANGES

## High-level view

The bootstrap edge function uses the primary key on the one-row guard as the serialization point, then releases it only when provisioning cannot complete. **Confirmed:** this resolves the prior concurrent first-owner bootstrap race.

The app still treats remote cloud sign-out as best effort even though its auth client persists sessions in `localStorage`. Clearing the SQLite configuration stops refresh and drops the in-memory client, but neither flow guarantees deletion of the persisted Supabase credential after an error.

## One-row guard serializes the initial cloud owner

`bootstrap-owner` inserts `owner_bootstrap_guard(id = true)` before querying `shops`. The primary key permits exactly one caller to claim that row; any concurrent caller receives a conflict instead of continuing to create another Auth user, shop, or owner membership. The handler removes the claim on its explicit failure paths, while a successful bootstrap retains it. **Confirmed:** the previously reported concurrent first-owner bootstrap race is resolved.

## Local state is cleared even if Supabase sign-out fails

The runtime client is created with `persistSession: true` and `globalThis.localStorage`, so its session outlives the current `supabase` instance. Both `signOutLocalAccount` and `disconnectSupabase` call `await signOutCloud().catch(() => undefined)`, then clear application state. On disconnect, `configureSupabase` only stops auto-refresh and nulls the client; it does not delete the persisted auth session. **Confirmed:** when remote sign-out returns an error, the app can show the local user as logged out or disconnected while the retained Supabase credential remains available to a later client configured for that project. The flows need a guaranteed local credential purge rather than swallowing the error and proceeding.
