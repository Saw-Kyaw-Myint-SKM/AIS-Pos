# Multi-device catalog synchronization

The change adds a catalog-only outbox, a cursor-based pull RPC, and a Sync screen reachable from Settings for all signed-in local roles. Item and category handlers persist their SQLite mutation before constructing an outbox snapshot, then attempt a background synchronization; the callback dependency lists include the values used by those handlers. The owner-only controls are hidden in the client, but the migration protocol itself is not protected at the server boundary, and non-owner devices have no usable cloud sign-in/provisioning path. **Watch for:** **confirmed** any active member can submit the same catalog snapshot operations that constitute a migration, so the owner-only migration rule is bypassable; **confirmed** staff and admin cannot establish the Supabase session required to pull the shared catalog through the shipped UI.  
**Verdict**: NEEDS_CHANGES

## High-level view

Catalog mutations now follow the intended offline-first sequence: SQLite commits first, then a post-commit snapshot is enqueued and pushed. The pull side correctly accepts active memberships at the RPC boundary, and the Settings-to-Sync route is not role-restricted, but it only works when a valid Supabase session already exists on that device.

The migration action is owner-only in the React view and callback, but it writes ordinary `category_upsert` and `item_upsert` operations. Since the catalog RPC authorizes all active roles for those operations, it cannot tell an owner-requested migration apart from a member-originated full catalog upload.

## Migration snapshots are accepted as ordinary member catalog writes

`markLocalMigrationRequested` in `src/sync.ts` sets local migration metadata and queues one `category_upsert` per category plus one `item_upsert` per item. It does not create a distinct remote migration operation or attach an owner-verifiable migration grant. `apply_catalog_sync_operation` in `supabase/migrations/202608310004_catalog_sync_rpc.sql` accepts those operation types after only checking that the caller has an active membership; it intentionally permits `owner`, `admin`, and `staff` alike.

The `SyncScreen` only renders the migration button for owners, and `requestLocalMigration` returns unless `membership.role === 'owner'`. That is presentation-level protection rather than enforcement of the migration contract. An active non-owner who sends the same supported RPC payloads can upload an entire local catalog. **confirmed** This violates the owner-only migration boundary; the server needs a distinct owner-authorized migration operation (or server-issued migration session) rather than inferring migration from otherwise member-authorized catalog upserts.

## Active members can open Sync but cannot authenticate into it

`SettingsScreen` renders the normal Sync row unconditionally, and `SyncScreen` enables sync for any non-null membership. `pull_catalog_changes` likewise calls `has_shop_role`, so an already-authenticated active owner, admin, or staff member is authorized to pull catalog changes.

However, `runSync` refuses to run without `membership`, and membership is derived from the persisted Supabase Auth session. The only client call to `signInWithEmail` is `completeCloudOwnerSignIn`; it rejects the session unless the membership role is `owner`. `CloudOwnerScreen` and its route are also owner-local-role-only. The added `create-staff` Edge Function has no client invocation. **confirmed** an admin or staff member on a separate device has no shipped flow to authenticate to Supabase and obtain the active membership required by Sync, so the multi-device pull requirement is not reachable for those roles despite the Settings entry.
