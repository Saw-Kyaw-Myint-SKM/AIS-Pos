# Multi-device catalog synchronization

The change adds a local outbox and Supabase catalog-change feed so devices can publish category/item mutations and pull the shared catalog by cursor. Category save, delete, and reorder handlers correctly write SQLite before they enqueue their corresponding category operations, preserving the intended local-first ordering for owners. However, the app only queues those operations for an owner and only exposes the Sync entry point to the local owner, while the backend is explicitly authorized for active owner, admin, and staff members. **Watch for:** **confirmed** admin and staff devices cannot reach Sync from Settings, and **confirmed** their catalog mutations are never enqueued, so the advertised multi-device catalog flow does not work for those roles. **Verdict**: NEEDS_CHANGES

## High-level view

The persistence layer assigns stable remote UUIDs to local categories and emits snapshots for creates, updates, and each member of a reordered list. The handlers invoke it only after the SQLite save, delete, or reorder has completed, so owner-originated category events describe committed local state.

The cloud RPCs allow every active shop membership to submit catalog operations and to read catalog change events. The client contradicts that policy: owner-only checks suppress both mutation outboxing and the Settings routes required for an admin or staff device to open Sync and pull those permitted changes.

Local migration remains client-gated to owners and the visible migration button is owner-only. Its callback has an incomplete dependency list, though, and a separate item-delete path queues a remote deletion before attempting its SQLite deletion.

<summary>Issues (5)</summary>

1. **Admin/staff catalog edits never leave the device** — **confirmed** `saveCategoryHandler`, `deleteCategoryHandler`, and `moveCategory` enqueue only when `membership.role === 'owner'`, even though the catalog RPC accepts any active role. Queue and sync catalog changes for active admin/staff members as well; retain owner-only gating only for migration and project administration.
2. **Sync is unreachable for admin/staff** — **confirmed** `SettingsScreen` renders Sync only when `canManageOwnerControls` is true, and `App.tsx` supplies that flag only for the local owner. Render the Sync route for signed-in roles, while keeping setup and migration controls owner-only.
3. **Item deletion can publish a deletion for an uncommitted local change** — **confirmed** `confirmDelete` queues and starts sync before `deleteClothingItem`. Delete locally first, then queue the remote delete, matching the category ordering and preventing divergence when SQLite rejects the deletion.
4. **Migration callback can use a stale shop identifier** — **confirmed** `requestLocalMigration` reads `membership.shopId` but depends only on `membership?.role`. Depend on the membership object or its shop ID so a membership refresh changing shops cannot submit migration against a captured shop.
5. **Multi-device sync behavior has no targeted coverage** — **confirmed** no workspace tests exercise category outbox ordering, role-specific Sync access/pull, migration authorization, or failed local deletes. Add focused unit or integration coverage before shipping the cross-device contract.

<summary>Details</summary>

## Category events reflect committed owner-side changes

**confirmed** `saveCategoryHandler` awaits `saveCategory` before `queueCategoryUpsert`, `deleteCategoryHandler` awaits `deleteCategory` before `queueCategoryDelete`, and `moveCategory` awaits the transactional `reorderCategories` before queueing snapshots for the complete reordered ID list. The outbox snapshot resolves a stable remote ID and reads the persisted category, so an owner’s successful save and reorder events carry the committed name, color, and position. The delete path correctly resolves the existing remote mapping after the local row is removed, avoiding an accidental new remote ID.

The same behavior is not available to admin or staff devices. **confirmed** every one of these category handlers wraps enqueueing in `membership?.role === 'owner'`; a local category mutation made by either permitted non-owner role is therefore refreshed locally but never enters `sync_outbox`. This conflicts with `apply_catalog_sync_operation`, which treats any active `shop_members` role as authorized. The client role check should be broadened to an active membership for normal catalog events, not removed from local migration.

## Sync UI denies roles that the change feed authorizes

**confirmed** `pull_catalog_changes` calls `has_shop_role`, whose default role set is owner, admin, and staff, and `runSync` only requires a non-null active membership.

**confirmed** the normal UI path prevents admin and staff from using it: `App.tsx` passes `canManageOwnerControls={account.role === 'owner'}`, and `SettingsScreen` places both the setup and Sync rows inside that owner-only condition. The Sync screen itself would allow a configured non-owner membership to run a pull and correctly omits migration controls, but those users cannot navigate there through Settings. Sync needs its own all-signed-in-member entry point; Supabase setup, cloud-owner bootstrapping, backup/restore, and migration can remain owner-only.

## Owner-only migration boundary is correct, but its closure is not

The migration button is rendered only for `role === 'owner'`, and `requestLocalMigration` independently returns unless the cloud membership is an owner. **confirmed** this keeps the privileged local bootstrap request out of admin and staff UI flows, while ordinary catalog sync can be made broader.

**confirmed** the callback sends `membership.shopId` but lists `membership?.role`, rather than the membership or shop ID, in its dependency array. If membership refresh replaces the current membership with another shop while preserving the owner role, a previously created callback can request migration for the old shop. Including `membership` or `membership?.shopId` makes the authorization value and target shop update together.

## Item removal breaks the local-commit-before-event rule

**confirmed** `confirmDelete` queues `queueItemDelete` and starts `syncNow(true)` before awaiting `deleteClothingItem`. A database failure can therefore publish a remote tombstone even though the item remains on the initiating device. Reordering the local delete ahead of `queueItemDelete` aligns item removal with the category handlers and makes the remote event represent a successful local mutation.

**confirmed** the workspace has no targeted tests for category event ordering, role-specific Sync navigation/pull behavior, owner-only migration, or the outbox ordering around failed deletes. These flows need focused tests before relying on the multi-device contract.
