# Offline-first catalog synchronization with Realtime wake-ups

The change adds a persisted Offline/Online device mode around the Supabase catalog path. Offline is the default for absent or invalid settings; Online requires an active project configuration, resolves an active membership, performs an initial sync, and then reacts to catalog event-log inserts. Realtime is deliberately used only to request another sync, while `pull_catalog_changes` advances the durable local cursor and applies the authoritative event stream. Watch for: no blocking client or server issue was found in the requested mode, subscription, cursor, or cleanup paths. **Verdict**: APPROVED

## High-level view

Mode state is held locally in SQLite and loaded defensively as Offline unless the exact saved value is `online`. Both the manual sync entry point and the subscription effect require Online mode, an active project configuration, and a membership, so configuring Supabase alone does not begin catalog synchronization.

The subscription watches only inserted `shop_change_events` rows for the member’s shop and invokes the normal sync runner. The runner pulls ordered, bounded event pages from the server and persists the last applied cursor transactionally, so dropped Realtime notifications and delete events remain recoverable.

Changing the mode, project configuration, or membership inputs causes the subscription effect to clean up its previous channel. Server-side membership checks constrain both cursor reads and Realtime-visible rows to the selected shop.

## Cursor pull remains the reconciliation authority

The Realtime callback from `subscribeToCatalogChanges` invokes `syncNow(true)` and does not consume the payload as catalog state. `runSync` instead requests ascending cursor pages, applies all category/item changes in a local transaction, and writes the resulting cursor with those changes. This preserves recovery for missed notifications and catalog tombstones.

## Subscription and configuration lifecycle

The subscription effect is enabled only for Online mode with an active configuration and membership. Its dependency set includes mode, configuration activation, membership, and the sync callback, so changing any of them tears down the prior channel; the returned cleanup removes the exact Supabase channel it created. The foreground handler is also mode-gated before requesting a pull.

## Event-log membership boundary

Catalog upserts/deletes flow through `record_shop_change` into `shop_change_events`, which is published to Realtime. RLS scopes event rows to active membership and `pull_catalog_changes` repeats `has_shop_role` within its security-definer query, leaving the server—not the client-side channel filter—as the boundary enforcement point.
