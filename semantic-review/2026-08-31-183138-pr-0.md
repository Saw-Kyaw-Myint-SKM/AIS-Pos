# Persisted Supabase session teardown without a runtime client

The latest auth teardown change covers the case where Supabase configuration has already removed the in-memory client. `signOut()` now deletes `clothes-pos-supabase-auth-session` directly from the installed Expo SQLite local-storage adapter when `supabase` is null; that is the same key supplied to `createClient` for persisted sessions. Both application teardown callers invoke this function before clearing either the local account session or Supabase project configuration. **Watch for:** no blocking issues found. **Verdict**: APPROVED

## High-level view

Session persistence is bound to one explicit storage key. Runtime-client teardown uses Supabase local-scope sign-out, while no-client teardown removes that same key directly, so both paths revoke the persisted credential without requiring a network request or client reconstruction.

## No-client teardown deletes the persisted credential

**Confirmed:** when `supabase` is null, `signOut()` calls `globalThis.localStorage.removeItem(CLOUD_AUTH_STORAGE_KEY)`. `CLOUD_AUTH_STORAGE_KEY` is the value passed as `auth.storageKey` when constructing the Supabase client, and the module installs Expo SQLite-backed local storage before either operation. This clears the persisted auth session even after `configureSupabase()` has stopped refresh and nulled the runtime client.

## Application teardown reaches the shared auth cleanup

**Confirmed:** local-account logout and Supabase-project disconnect both await `signOutCloud()` before removing their respective local session/configuration records. A missing runtime client therefore takes the direct persisted-key removal path rather than silently returning with the token intact.
