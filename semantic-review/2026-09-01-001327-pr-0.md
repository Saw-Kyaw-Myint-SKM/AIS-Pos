# Member catalog pull with owner-local publishing

The client blocks catalog controls for signed-in non-owner cloud members while the owner path writes to SQLite, queues a catalog operation, and starts Sync afterward. Member sign-in accepts active cloud memberships and routes back to Sync, where every signed-in role can start synchronization. **Watch for: confirmed — a member device with pending or failed catalog outbox work attempts to push first; that failure stops the run before catalog pull. Confirmed — the form routes and save/delete callbacks remain ungated at the App boundary, so a route or callback wiring regression can mutate a member’s local catalog.**

**Verdict**: NEEDS_CHANGES

## High-level view

The visible catalog surface uses `editable={!membership || membership.role === 'owner'}`. Cloud Admin and Staff members lose creation, edit, and deletion entry points; owner writes remain local-first and queue only after SQLite succeeds.

Member authentication accepts any active membership and lands on Sync. Since Sync is push-then-pull for every role, a member’s ability to pull currently depends on the local outbox being empty and pushable.

The catalog form routes still receive mutating callbacks regardless of membership. The UI gate prevents ordinary navigation today, but persistence itself does not enforce the owner restriction.

## Member outbox work stops the catalog pull

`completeCloudMemberSignIn` accepts an active owner, admin, or staff membership and sends it to Sync. `runSync` selects every pending or failed outbox row and invokes a push RPC before `pullCatalogChanges`; a push error, conflict, or rejected result sets `pushFailed`, and the pull is skipped.

This is a **confirmed** client-side availability gap. A device with pending catalog work from prior owner use, an interrupted migration, or a retryable failure can sign in as a non-owner but cannot pull until that unrelated work clears or becomes pushable. Member behavior should pull its shop cursor without attempting local publication, while the owner retains the existing queue-then-sync path.

## UI permission is not enforced at catalog persistence

`ItemsScreen` and `CategoriesScreen` correctly hide catalog mutations when the cloud membership is not `owner`; owner callbacks write locally, then queue the matching snapshot or delete operation. But `App.tsx` always renders `itemForm` and `categoryForm` with those same save/delete callbacks. None rejects a non-owner before `saveClothingItem`, `saveCategory`, `deleteCategory`, `reorderCategories`, or `deleteClothingItem` executes.

This is **confirmed** by the unconditional route branches and persistence calls. A stale or future route transition to either form bypasses the display-level gate and creates a local-only member mutation because queueing remains owner-only. Keep the UI gate, but fail closed at the callback boundary for an active non-owner membership and prevent non-owner form-route rendering.
