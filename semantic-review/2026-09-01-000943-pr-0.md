# Owner-published catalog sync with member access

This change adds a durable local catalog outbox, UUID entity mapping, cursor-based catalog pull, and cloud sign-in surfaces around the existing SQLite catalog. Owners queue local item and category mutations, migration snapshots categories before items, and a manual sync drains the outbox before reconciling remote changes atomically with the saved pull cursor. Sync itself is available to every signed-in local role; the cloud member path accepts any active membership, while Supabase configuration and migration controls are gated to local Owners. **Watch for: confirmed — Admin and Staff can still mutate the catalog locally, but their mutations are never put in the outbox, creating device-specific catalog forks.**

**Verdict**: NEEDS_CHANGES

## High-level view

The client follows a push-then-pull model: owner catalog writes are queued with persistent remote IDs, then a successful drain fetches catalog events after the device cursor and commits each page with its cursor advance. The local-first owner migration queues category snapshots before item snapshots, preserving category references during the initial publish.

The Sync screen is reachable from Settings for every local role, member sign-in accepts active owner/admin/staff memberships, and only a cloud Owner sees or can invoke migration. This access structure is correctly separated from the Owner-only project-configuration route.

Catalog editing is not separated the same way. The shared Items screen exposes create, edit, reorder, and delete actions to every local account, but the callbacks only queue those actions when cloud membership is `owner`; after a member edits, a sync has no local operation to publish or reconcile that edit.

## Admin and Staff can create unsynchronized catalog forks

`ItemsScreen` receives no role or mutability constraint, so every signed-in account can open product/category forms, delete catalog rows, and reorder categories. Its callbacks in `App.tsx` persist each change to SQLite first. The subsequent `queueItemUpsert`, `queueItemDelete`, `queueCategoryUpsert`, `queueCategoryDelete`, and `queueCategoryReorder` calls are all conditional on `membership?.role === 'owner'`.

This is a confirmed catalog-consistency failure for a configured shop. An Admin or Staff can change stock, price, category assignment, category ordering, or delete a product on one device; the next Sync has no outbox record for that local mutation. The cursor pull only applies newer remote events, so it does not reliably restore the unchanged remote record either. The device can therefore keep selling from a divergent catalog until an unrelated remote event overwrites part of it. The client needs to prevent member catalog mutations under this owner-publishing model.
