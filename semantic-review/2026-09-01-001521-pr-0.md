# Pull-only member catalog sync and owner-gated catalog writes

The multi-device catalog client now separates member synchronization from the owner publishing path. `runSync` immediately pulls remote catalog changes for any active non-owner membership, so pending, failed, or recovered `syncing` outbox rows remain local state and cannot cause a push attempt or block the pull. Catalog controls remain hidden for non-owners, and the App-level save, delete, reorder, and migration callbacks now reject active non-owner memberships before a SQLite write or queue operation; the item and category form routes are also not rendered for those memberships. **Watch for: no remaining client-side blocker identified.**

**Verdict**: APPROVED

## High-level view

Non-owner sync now follows a pull-only path after interrupted operations are normalized back to pending. It invokes the catalog cursor RPC and updates the cursor and last-sync timestamp without reading or dispatching `sync_outbox`, so stale owner-created work cannot prevent a member device from receiving catalog updates.

Catalog permissions are enforced at both presentation and action boundaries. `ItemsScreen` and `CategoriesScreen` stay read-only for a non-owner, while the App callbacks independently stop all item/category persistence, deletion, category reordering, migration queueing, and form rendering for that membership.

## Non-owner sync bypasses stale catalog outbox work

`runSync` first recovers interrupted rows by marking `syncing` records pending, then branches on `membership.role`. For `admin` and `staff`, the branch calls `pullCatalogChanges`, records a successful pull, and returns before the outbox query and RPC-dispatch loop. This is **confirmed** pull-only behavior: stale pending, failed, or formerly syncing rows can still be displayed in sync status, but they cannot be uploaded and do not gate the catalog pull.

## Catalog mutation routes fail closed for non-owners

The catalog UI is read-only when an active membership is not `owner`, and the persistence callbacks repeat the same restriction before `saveClothingItem`, `saveCategory`, `deleteCategory`, `reorderCategories`, and `deleteClothingItem`. The callbacks consequently cannot alter local catalog state or create fresh outbox work if a stale route, future navigation path, or direct callback wiring reaches them as a member. This is **confirmed** by the early membership checks preceding every catalog mutation.

`itemForm` and `categoryForm` additionally require either no cloud membership or an owner membership before rendering. A non-owner route transition therefore produces no editable form, closing the route-level bypass in addition to the callback-level one. Owner-only migration initiation is guarded in the same manner.
