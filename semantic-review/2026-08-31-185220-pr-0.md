# Offline catalog migration and product sync

The new owner-only catalog sync assigns stable remote UUIDs to local categories and products, persists operations in a SQLite outbox, and replays them through `apply_sync_operation`. The initial migration queues category snapshots before product snapshots, while later product saves and deletes add snapshots to that queue. The implementation cannot safely upload the local catalog to the deployed RPC: catalog mutations are not reliably enqueued after membership becomes available, their replay order is not deterministic, and the RPC drops two persisted product fields. Watch for: **confirmed** product edits/deletes commonly never reach the outbox; **confirmed** product QR codes and category assignments are silently lost on the server; **confirmed** rapid mutation sequences can replay in an order that resurrects stale catalog state.

**Verdict**: NEEDS_CHANGES

## High-level view

The client maps SQLite integer keys to stable UUIDs per shop, but the product save/delete callbacks capture membership before the asynchronous cloud membership load. **Confirmed:** after that load, an owner still saves locally without queuing catalog operations.

The outbox has no monotonic sequence and sync reads rows only by second-resolution `created_at`. **Confirmed:** initial migration and quick edits can share that value, allowing a later delete or update to precede an earlier upsert.

The deployed RPC accepts UUID product IDs but its `item_upsert` statement neither inserts nor updates `qr_code` or `category_id`. **Confirmed:** migrated and subsequently saved products lose their barcode and category relationship on the server.

<summary>Issues (3)</summary>

1. **Stale membership bypasses catalog enqueue** — Add `membership` (or the required owner/shop values) to the `saveItem` and `confirmDelete` callback dependencies, then cover a membership transition followed by a save/delete.
2. **Outbox replay has no deterministic mutation order** — Store an ordered sequence (or order ties by an insertion key) and replay it consistently so initial snapshots and rapid upsert/delete operations cannot be reordered.
3. **RPC discards barcode and category mapping** — Extend `apply_sync_operation` to validate, insert, and update `qr_code` and `category_id` from the UUID payload before enabling catalog migration.

<details>
<summary>Details</summary>

## Owner membership is captured before cloud sync becomes available

`PosApp` creates both `saveItem` and `confirmDelete` with dependency lists that omit `membership` (`App.tsx`, around the product handlers). The later bootstrap effect calls `setMembership(...)`, but React retains those callbacks because none of their listed dependencies changed. Their `membership?.role === 'owner'` guards therefore continue to evaluate the initial `null` value. **Confirmed:** an owner can edit or delete inventory locally after signing in and no `queueItemUpsert` or `queueItemDelete` call is made, so the remote catalog permanently misses those later changes.

The local write happens before the conditional queue attempt for saves; deletes proceed without a queued deletion. This is not a delayed sync: the mutation has no outbox representation. Include membership in both dependency arrays (or pass a current owner/shop identity to the handlers) and exercise the bootstrap/sign-in transition in a test.

## Timestamp ties can replay catalog history out of order

`markLocalMigrationRequested` inserts all category and item operations in one transaction, and product saves/deletes append additional operations. SQLite gives each `sync_outbox` row `CURRENT_TIMESTAMP`, which has second precision. `runSync` subsequently selects every pending or failed operation with only `ORDER BY created_at ASC` (`src/sync.ts`). **Confirmed:** rows created in the same second have equal sort keys; their relative order is unspecified.

For a product changed or deleted soon after it is created, the server may process the delete before an older upsert and restore the deleted product, or process an older snapshot after a newer one and overwrite it. This also makes the intended category-before-product migration ordering non-binding once category references are implemented. Persist a monotonic local sequence at enqueue time and order by it; retry selection must use the same ordering.

## The RPC accepts product UUIDs but omits two catalog fields

`queueItemSnapshot` sends `qrCode` and a mapped `categoryId` for every product, and the remote schema contains `items.qr_code` and `items.category_id` (`202608310001_offline_pos_foundation.sql`). The current `apply_sync_operation` implementation in `202608310002_owner_offline_sync_foundation.sql` handles `item_upsert` by inserting/updating name, size, price, cost, stock, choice, color, photo path, and note only. It does not mention either `qr_code` or `category_id`. **Confirmed:** the RPC returns `completed` while silently storing its default/null values for these fields.

Migration therefore appears successful while server barcode lookup and category-filtered catalog state diverge from the local source. The RPC must parse and validate the optional UUID category payload, enforce that it belongs to the same shop, and include both fields in its insert and conflict-update clauses.
